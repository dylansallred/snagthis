# SnagThis for Chrome

The free extension finds videos on the current page and saves supported direct MP4/WebM files through Chrome, without the desktop app. Streams, extraction, audio/subtitle processing, and the SnagThis library use the optional local desktop app. Both download paths continue when the popup closes. Chrome Web Store is the intended installation and automatic-update channel; a published listing is not yet available. The following **Load unpacked** steps are for development and the manual ZIP fallback if store approval is unavailable. Chrome 112 or later is required.

1. From the repository root, run `npm run build:extension:css`. This also copies the shared row/playlist contracts and the bundled Inter font into the extension.
2. Open `chrome://extensions`, enable Developer mode, choose **Load unpacked**, and select `apps/extension`.
3. For streams or desktop features, start the SnagThis desktop app. Skip pairing for supported direct-file downloads in Chrome.
4. In Chrome, click **Extensions** (the puzzle icon) → **SnagThis**. While the desktop app shows **Waiting for Chrome…** (first run, or Settings → Chrome extension), the popup asks by itself; otherwise choose **Connect** in its banner. SnagThis shows the same four digits without taking focus (no `snagthis://` link while it is running); choose **Allow** there if they match the popup. The code fallback is under the banner's ⋯ → **Use a code instead**, with **Settings → Chrome extension → Show connection code** in the desktop app. Keep the desktop app open while downloading. The extension remembers its own private local-app credential.
5. Play a video on a page, open SnagThis in the toolbar, and choose **Download**.

The 480px popup shows one video per row, with a clear thumbnail and a compact progress lane below active rows. Pause, resume, retry, and saved-file actions appear when relevant; quality selection uses real discovered variants. Chrome downloads finish as **Saved in Chrome** with **Show in folder**. The **⋯** button (shown on row hover or keyboard focus) or a right-click opens download details, cancel, rename, hide, preview, subtitles, and **Show all detected streams**. Choose **Download with desktop** before starting a direct file if you want it in the desktop library. Settings groups quality, subtitles, and desktop notification preferences; desktop folder changes and Advanced settings open the app.

Detection observes standard fetch/XHR responses, video elements, and Chrome's request events in every frame. HLS can be recognized by its filename, response type, or playlist body, including small and extensionless playlists. Raw video pieces are excluded, and DASH manifests are read for their duration, protection and segment pattern. Master playlists collapse only explicitly referenced variants, or videos with identical known duration on the same page; filenames and timing alone never establish identity. Page navigation resets the list. In unpacked development builds, YouTube watch-page metadata is sent as a page URL for the desktop's extractor; the packaged store build lists the page, muted, with “SnagThis doesn't save videos from this site” and no action, and never downloads or hands it off (see [extension distribution](../../docs/extension-release.md#youtube-in-the-store-build)). Request headers and cookies come only from Chrome's network events; media URLs reported by page scripts are untrusted hints.

Thumbnails use source-specific video posters, representative readable frames, or bounded source previews. Generic page artwork is rejected; YouTube artwork must match the known video identity. Page frames are prepared during natural playback only when they reach a representative scene range. Frame data is bounded to a 20 KB JPEG data URL. A neutral loading thumbnail appears while an image is unavailable. Unsupported formats can be detected without being downloadable.

**DRM-protected video is never saved.** When a page's player uses Encrypted Media Extensions (Widevine, PlayReady, FairPlay), or its DASH manifest has `ContentProtection` or its HLS playlist uses `SAMPLE-AES` DRM keys, the popup shows one row, `Protected by {site} (DRM) — SnagThis can't save it`, with a **Why?** explanation and no Download or desktop handoff. SnagThis only observes these signals (the key system the page requested, MediaKeys on its player, `encrypted` events, and `pssh`/`tenc` boxes in init segments the page already fetched); it never decrypts, records, screen-captures or reads frames from protected video. Plain AES-128 HLS is not DRM and stays downloadable. Individual stream pieces (fMP4/CMAF fragments, init segments, byte ranges) are grouped into their stream rather than listed; **Show all detected streams** still shows them.

Media headers are retained only with the observed media URL in trusted `chrome.storage.session`; they are sent to the paired desktop only after a user starts a desktop download. Chrome downloads use Chrome's native request/session handling without replaying captured headers; sites that require special headers may refuse the browser download and need the desktop path. App credentials are stored in trusted `chrome.storage.local` and are never injected into pages. Navigation and tab closure clear page detections. The main page observer and isolated metadata collector have been rewritten around browser APIs; see the repository's provenance record for the inherited title helpers and bundled HLS player license.

The queue is polled once per second while the popup is open; desktop health is checked every two seconds. Supported direct files remain downloadable when the app is closed or unpaired. Other videos offer **Use desktop app**. **Open SnagThis** uses its protocol handler and changes to **Get the app** if it remains unavailable. Chrome controls its own save location, safety prompts, and resume support. Chrome downloads do not appear in SnagThis's desktop library. An expired desktop link offers **Open page**; after recapture, right-click **Continue previous download** when one failed desktop job belongs to that exact source page. The engine validates the refreshed media before reusing downloaded pieces.

Development previews render the real popup with the original Pixel worlds sample clips and isolated sample data: serve the repository over loopback HTTP, then open `apps/extension/popup.html?demo=default`. Other modes are `empty`, `loading`, `error`, `offline`, `quality`, `audio`, `settings`, `states`, `snag`, `problem`, `pairing` and `version`; `pairing` takes `&pair=starting`, `waiting`, `connected`, `denied`, `blocked`, `expired`, `conflict`, `limited`, `offline`, `failed` or `code` (add `&build=store` to hide the DEV BUILD chip). Demo code never sends API writes. Unpacked fixture tests can choose a tab with `?tab=<id>` and a loopback API with `&apiBase=http://127.0.0.1:<port>`; remote API overrides are rejected.

Run `npm run package:extension` from the repository root to build `snagthis-extension.zip`. The deterministic package contains only reviewed runtime files and licenses; development previews and sample movies stay in the repository. See [extension distribution and updates](../../docs/extension-release.md) for the store submission requirements, versioning, permission declarations, and update compatibility.

Store-installed copies receive updates through Chrome after the release passes store review. For a developer/manual ZIP copy, replace the files in the same stable folder, choose **Reload** on the existing installation at `chrome://extensions`, then refresh the video page (SnagThis also attaches to already-open pages after an install or update, or asks you to refresh when Chrome does not allow that). Do not uninstall/reinstall to update. Pairing, preferences, and Chrome-download references survive a same-ID update, while temporary detections, headers, prepared posters, and desktop tab/job mappings are intentionally cleared. Chrome owns native downloads and files; desktop downloads and saved files remain in the app. Manual ZIP installs do not update automatically.
