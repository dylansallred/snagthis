Why the popup shows “Connected” again the next time it opens

Chrome closes the popup the moment SnagThis takes focus, so the extension defers the outcome to the next opening. On Allow, the service worker stores the finished request in chrome.storage.session['snagthis:pairing'] as { status: 'connected' } and paints a green ✓ badge (apps/extension/service-worker.js:435-441, finishPairing: line 439 stores the state, line 440 sets the badge). Every popup opening asks the worker for that state and, if it says connected, draws the full-screen celebration sheet (apps/extension/popup.js:1245-1248 → celebrateConnection() at popup.js:945-958, with a focused Done at line 951). Only then does it send PAIR_ACK (line 957), which clears the state and badge (service-worker.js:494-499). The same path replays Denied, Timed out and the other outcomes as full sheets (popup.js:1248 → renderPairing). This is working as specified: design spec §8 “Outcomes” says “the next popup opening celebrates once the same way … focus on Done”. So removing it is a spec change, not a bug fix.

Shared across all three options

  • SnagThis comes forward by itself. A new request from an extension makes the desktop show its approve card without the snagthis://open/pair hop, so Chrome’s own “Open SnagThis?” prompt only appears when SnagThis has to be launched. Rate limits (3 per 5 min per extension, 30 global), the extension-origin check and the 1-hour block after Deny stay as they are.
  • Digits side by side. On macOS the card is shown with showInactive() (Windows: shown without activation, taskbar flash), so Chrome keeps focus and the popup stays open until the person clicks Allow. Today the popup closes first and the person compares against a 4-character toolbar badge.
  • Everything closes itself. Allow turns the card into a one-second “Connected” and it closes; if SnagThis was hidden before, it hides again. No Done on either side.
  • No sheet on reopen. The worker still records the outcome, but the popup shows it as a two-second green line in the banner slot (or nothing, in C) and the list is usable at once. Denied and timed-out outcomes become one amber sentence and one button in the same slot, per the “silence when healthy” rule.
  • Code fallback stays. It moves out of the main path into popup Settings ▸ Connection (“Use a code instead”) and desktop Settings ▸ Chrome extension (“Show connection code”), unchanged: six digits, five-minute expiry.

Local Network Access and other Chrome-owned prompts

  • Local Network Access: no LNA handling exists in the code and none was seen in these captures. Every bridge request comes from the extension’s own origin (worker or popup) to http://127.0.0.1:49732, which the manifest lists in host_permissions. We believe Chrome exempts extension-origin requests with matching host permissions from the LNA prompt, which is aimed at web pages. Check this on current Chrome Stable before building any option. If Chrome does prompt, the prompt is Chrome’s and appears once. Each option then shows one line in its waiting slot: “Chrome is asking to let SnagThis reach this computer. Choose Allow in Chrome’s prompt.” A blocked request stays distinguishable from “SnagThis isn’t open” because /v1/health fails the same way, so the popup should say “Can’t reach SnagThis” and offer both fixes.
  • “Open SnagThis?”: today the worker always opens snagthis://open/pair with chrome.tabs.create, which makes Chrome ask before launching an external app (its checkbox can remember the choice). That prompt couldn’t be captured in headless Chromium, so the storyboard shows it as a mock. The options keep it only for launching an app that isn’t running.
  • Web Store vs unpacked: unchanged. The popup’s DEV BUILD chip and the desktop’s Not Web Store / ✓ Web Store tag stay on the approve card’s identity line.
