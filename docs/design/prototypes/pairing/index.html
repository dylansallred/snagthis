What the connection protects, today

  • The bridge. The desktop serves 127.0.0.1:49732. Without a token, any local process or web page could queue downloads or read the library. A Host allowlist (127.0.0.1 / localhost / [::1]:port) blocks DNS-rebinding pages. An Origin allowlist (null and file:// for the desktop renderer, plus approved chrome-extension:// IDs) blocks other web pages. Every route except /v1/health and /v1/pair/complete needs the Bearer token.
  • The pairing code is the only thing that turns an unknown extension origin into an approved one and hands it the token. It is 6 digits, lasts 5 minutes, can be used once, is compared in constant time, allows 10 tries per 5 minutes, and is shown only in the trusted desktop UI. /v1/pair/complete accepts any chrome-extension:// origin, so the code, not the extension ID, is the proof.
  • Limits. A local process is not a browser, so it can forge any Origin. The origin checks only stop web pages. A process running as the same user can read bridge-auth.json (0600) directly, so no pairing UX defends against same-user malware; the goal is to stop websites, other extensions and blind local probes. The pairing limiter counts all loopback traffic together, so a local process can use up the 10 tries and block pairing (denial of service only).
  • Gaps any redesign must handle. (1) null is a trusted origin, and a sandboxed iframe on any website also sends Origin: null. A new unauthenticated “request pairing” route must require chrome-extension:// and must not reuse originAllowed() as is. (2) There is one shared bridge token and no revoke route. A real Disconnect needs a token per extension (origin → token), or rotating the shared token, which disconnects every client.

Prototype only. Nothing connects, copies or opens. Every option keeps: confirmation or secret proof through the trusted desktop UI, rate limits, expiry, the extension origin allowlist, and no token for web pages.
